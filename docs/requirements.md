# Требования к системе «AuctionDesk»

Автор: Григорьев Никита Егорович, группа 9/2-РПО-24/1. Тема: 14. AuctionDesk — Аукционная площадка.

## 1. Назначение и пользователи

**Предметная область:** учёт лотов, участников, ставок и завершения торгов на аукционной площадке.

**Задача системы:** выставление лота с ограниченным временем торгов, приём ставок участников, автоматическое определение победителя по максимальной ставке и фиксация результата.

**Пользователи:** продавец лота (создаёт лот, завершает торги досрочно) и покупатель (делает ставки). Текущий пользователь выбирается из списка участников, отдельная система аутентификации в границы проекта не входит.

## 2. Основные функции

| ID | Функция | Ожидаемое поведение и условие приёмки |
| --- | --- | --- |
| FR-01 | Просмотр каталога лотов | После нажатия «Подключиться» таблица показывает все лоты с названием, категорией, начальной и текущей ценой, продавцом, оставшимся временем, датой окончания и победителем. Данные читаются из SQL Server через JOIN четырёх таблиц |
| FR-02 | Создание лота | Пользователь вводит название, описание, начальную цену, выбирает категорию и задаёт длительность в минутах и секундах. После сохранения лот появляется в каталоге со статусом `active`, текущая цена равна начальной, дата окончания пустая, таймер начинает отсчёт |
| FR-03 | Внесение ставки | Пользователь выбирает активный лот и нажимает «Сделать ставку». Цена увеличивается на 500 ₽, запись добавляется в `bids`, история обновляется. При нарушении BR-01 — BR-03 операция отклоняется с сообщением |
| FR-04 | Завершение лота и архивирование | Продавец нажимает «Завершить» и подтверждает действие. Статус лота меняется на `completed`, определяется победитель по максимальной ставке, запись добавляется в `winners`, заполняется фактическая дата окончания. Лот остаётся в каталоге как архивная запись |
| FR-05 | Автоматическое завершение по времени | Таймер с интервалом 1 секунда обновляет обратный отсчёт. При достижении нуля лот закрывается автоматически, победитель определяется тем же способом, что и при ручном завершении |
| FR-06 | Поиск и фильтрация | Ввод части названия и нажатие «Найти» оставляет только совпадающие лоты. Выбор категории ограничивает вывод этой категорией, пункт «Все категории» снимает фильтр. При отсутствии совпадений таблица пуста |
| FR-07 | История ставок | При выборе лота правая панель автоматически показывает все его ставки: участник, сумма, время. Сортировка по убыванию суммы |
| FR-08 | Агрегированный отчёт | Представление `vw_lot_report` возвращает по каждой категории количество лотов, количество завершённых лотов и суммарную выручку по таблице `winners` |

Обязательный минимум: создание, чтение, изменение данных; архивирование вместо удаления; поиск и фильтрация; JOIN; четыре бизнес-правила; транзакционная операция; агрегированный отчёт.

## 4. Бизнес-правила

| ID | Правило своей предметной области | Когда проверяется | Что происходит при нарушении |
| --- | --- | --- | --- |
| BR-01 | Новая ставка должна быть строго выше текущей цены лота | Внутри транзакции TX-01 после чтения текущей цены с блокировкой строки | Сообщение «Ставка должна быть выше {сумма} руб.», транзакция откатывается, записи в `bids` нет, `current_price` не изменён |
| BR-02 | После закрытия лота и после истечения времени торгов ставки запрещены | Внутри транзакции TX-01 при проверке статуса и срока лота | Сообщение «Аукцион завершён, ставки запрещены» либо «Время аукциона истекло», транзакция откатывается |
| BR-03 | Продавец лота не может делать ставки на собственный лот | Внутри транзакции TX-01 при сравнении `seller_id` и текущего пользователя | Сообщение «Продавец не может ставить на свой лот», транзакция откатывается |
| BR-04 | Завершить лот вручную может только его продавец | При выполнении операции завершения: кнопка активна только для продавца, дополнительная проверка внутри транзакции | Кнопка неактивна для остальных пользователей; при программном вызове сообщение «Завершить может только продавец лота», статус лота не меняется |

## 5. Транзакционный сценарий TX-01

**Название операции:** внесение ставки на лот.

**Цель:** проверка актуального максимума, фиксация ставки и обновление текущей цены должны составлять единое действие. Если проверку и запись разнести, два участника смогут одновременно пройти проверку по одной и той же цене, и в `bids` появятся ставки, не соответствующие итоговой цене лота.

**Начальное состояние:** лот со статусом `active`, не истёкшим сроком `end_date`, заполненной `current_price`. Текущий пользователь существует в `users` и не является продавцом лота.

**Проверяемые правила:** BR-01, BR-02, BR-03.

**Изменяемые данные:** таблица `bids` — новая запись со ставкой; таблица `lots` — поле `current_price` выбранного лота.

**Последовательность:**

1. Начало транзакции `conn.BeginTransaction()`.
2. Чтение `current_price`, `status`, `seller_id`, `end_date` из `lots` с блокировкой строки `WITH (UPDLOCK)` внутри транзакции.
3. Проверка статуса лота и срока торгов (BR-02).
4. Проверка, что текущий пользователь не продавец (BR-03).
5. Проверка, что сумма ставки выше текущей цены (BR-01).
6. Вставка записи в `bids` с параметрами `lot_id`, `user_id`, `bid_amount`.
7. Обновление `current_price` в `lots` на сумму принятой ставки.
8. Фиксация всех изменений `transaction.Commit()`.

**Ошибка и откат:** отказ возможен на шагах 3–5 при нарушении бизнес-правил и на шагах 6–7 при ошибке SQL. В любом случае вызывается `transaction.Rollback()`, ни одна запись не сохраняется. Проверка запросами до и после попытки: `SELECT COUNT(*) FROM bids WHERE lot_id = 1` и `SELECT current_price FROM lots WHERE lot_id = 1` — оба значения должны остаться прежними.

**Параллельные операции:** операция конкурирует за цену одного лота. Проверка максимума и запись выполняются в одной транзакции, чтение лота блокируется подсказкой `UPDLOCK`, поэтому вторая параллельная транзакция ожидает завершения первой и читает уже обновлённую цену. Уровень изоляции — `READ COMMITTED` по умолчанию. Дополнительно на уровне БД действует ограничение `CHECK (bid_amount > 0)`.

## 6. Данные и ограничения

| Таблица | Назначение | Первичный ключ | Основные связи | Ограничения |
| --- | --- | --- | --- | --- |
| users | Участники аукциона | user_id | 1:M к lots по seller_id и winner_id, 1:M к bids, 1:M к winners | username NOT NULL, UNIQUE |
| categories | Категории лотов | category_id | 1:M к lots | category_name NOT NULL, UNIQUE |
| lots | Лоты, каждый является отдельным аукционом | lot_id | M:1 к categories, M:1 к users (продавец), M:1 к users (победитель), 1:M к bids, 1:1 к winners | starting_price > 0, duration_seconds > 0, status IN ('active','completed'), finished_date NULL до завершения, winner_id NULL до завершения |
| bids | Ставки участников | bid_id | M:1 к lots, M:1 к users | bid_amount > 0, bid_time DEFAULT GETDATE() |
| winners | Победители завершённых лотов | winner_id | M:1 к lots, M:1 к users | lot_id UNIQUE, final_price > 0, win_date DEFAULT GETDATE() |

Отношений «многие ко многим» в предметной области нет, таблица связей не требуется. Детали и ER-диаграмма: [модель данных](database-schema.md).

## 7. Интерфейс и отчёт

**Функциональные разделы:**

1. Каталог лотов — основная таблица с поиском, фильтром по категории, кнопкой создания лота и обратным отсчётом.
2. Панель истории ставок — автоматически показывает ставки выбранного лота, содержит кнопки «Сделать ставку» и «Завершить».
3. Форма создания лота — отдельное модальное окно с полями названия, описания, цены, категории и длительности торгов.

**Поиск и фильтрация:** поиск по части названия лота через `LIKE @search`, фильтр по категории через выпадающий список с пунктом «Все категории». Условия комбинируются. При отсутствии совпадений таблица остаётся пустой, приложение не выдаёт ошибку.

**Отчёт:** представление `vw_lot_report` агрегирует данные по категориям: общее количество лотов, количество лотов со статусом `completed` и суммарная выручка по таблице `winners`. Группировка по `category_name`, фильтр по периоду не предусмотрен.

**Проверка ввода:** название лота обязательно; цена — положительное число; категория обязательна; минуты — целое число не меньше нуля, секунды — от 0 до 59, суммарная длительность больше нуля. При нарушении выводится сообщение с указанием некорректного поля.

**Подтверждение операций:** ручное завершение лота требует подтверждения в диалоге «Да / Нет».

## 8. Технические требования

- C#, WPF, Microsoft SQL Server.
- Доступ к данным через ADO.NET и `Microsoft.Data.SqlClient`.
- Пользовательские значения передаются через `SqlParameter`.
- Предметная логика и доступ к данным отделены от интерфейса: слой `Models`, слой `Data` с репозиториями, слой `ViewModels`, слой `Views`. SQL-запросы размещены только в репозиториях.
- Соединения, команды и читатели освобождаются через `using`.
- При ошибке приложение показывает понятное сообщение без паролей и секретов.
- Проект разворачивается на другом учебном компьютере по README и SQL-скриптам.

Выбранные версии и дополнительные инструменты: .NET 8.0, WPF, MVVM без внедрения зависимостей, EF Core не используется, доступ к данным только через ADO.NET.

## 9. Границы проекта

**Входит в работу:** создание и чтение лотов, изменение цены при ставках, архивирование лота через статус `completed`, поиск и фильтрация, история ставок, четыре бизнес-правила, транзакция внесения ставки, автоматическое завершение по таймеру, агрегированный отчёт по категориям, выбор текущего пользователя.

**Не входит в работу:** аутентификация по паролю и разграничение прав на уровне БД, ввод произвольной суммы ставки, уведомления в реальном времени, импорт лотов из файлов, экспорт отчётов, отдельный экран отчёта в интерфейсе, мобильная и веб-версии.

**Согласованные уточнения:** сущности `auctions` и `lots` объединены в одну таблицу `lots`: каждый лот является самостоятельным аукционом со своей длительностью и победителем. Модель содержит 5 связанных таблиц, что соответствует требованию 5–7 таблиц. Удаление лотов заменено архивированием через статус, так как история ставок и победители должны сохраняться. Отчёт реализован представлением БД и проверяется запросом в SSMS.
